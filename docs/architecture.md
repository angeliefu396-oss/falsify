# 架构

## 目标与非目标

**目标**：同一套认知规则，在任意支持系统提示词或技能目录的 agent 上都能装、都能用；能机械检查的部分不依赖模型记性；规则改动可审计、可回归。

**非目标**：不做模型微调，不做向量检索，不做多 agent 编排，不声称提示词能提供技术隔离、跨会话自动记忆或独立审计。

## 三层

```text
┌─────────────────────────────────────────────────────────────┐
│ 载体层（四选一，内容同源）                                    │
│  SKILL.md  ·  AGENTS.md 内核段  ·  dist/falsify-single-file.md  ·  CLI │
├─────────────────────────────────────────────────────────────┤
│ 常驻内核 kernel/core.md       每轮生效，约 1,800 字符          │
│  身份 · 八步循环 · 六条铁律 · 输出合同 · 预测纪律 · 权限 · 自检 │
├─────────────────────────────────────────────────────────────┤
│ 工作流 references/01…19      按任务读一个，读完即弃            │
│  内核全文 · 证据分层 · 路由 · 呈现 · 审计 · 风险 · 研究 ·      │
│  决策 · 执行 · 系统构建 · 预测 · 状态 · 质量 · 边界 · 命令 ·   │
│  纪律 · 依据 · 模板 · 回归测试                                │
├─────────────────────────────────────────────────────────────┤
│ 强制层 scripts/falsify.py       0 上下文成本，拒绝非法写入         │
│  概率所有权 · 只追加 · 兑现封闭 · 封印链 · Brier · 小样本护栏  │
└─────────────────────────────────────────────────────────────┘
```

## 为什么不是一个大文件

`dist/falsify-single-file.md` 是存在的（给只能贴提示词的聊天框用），但它有代价：

| 形态 | 每轮成本 | 说明 |
|---|---:|---|
| 只挂内核 | ≈1,800 字符 | 一次性问题、闲聊、轻任务 |
| 内核 + 一个工作流 | ≈3,200 字符 | 典型严肃任务 |
| 单文件全量 | ≈29,700 字符 | 只在没有文件读写能力时使用 |

单文件全量不是"更完整"，是**注意力预算更贵**：长上下文里靠后的规则更容易被稀释，模型也更容易只执行前几段。渐进披露不是省 token 的花招，是让当前任务的规则**离当前回答最近**。

## 单一真源与生成物

```text
kernel/core.md ──┐
                 ├─→ scripts/build.py ─→ SKILL.md（内核区块）
references/*.md ─┘                    ├→ dist/kernel-always-on.md
                                      └→ dist/falsify-single-file.md
```

规则：

1. 手写只发生在 `kernel/core.md` 与 `references/`。
2. `SKILL.md` 的内核区间、`dist/` 全部是生成物，**手改即 PR 拒绝**。
3. `python scripts/build.py --check` 在 CI 与本地测试里跑；生成物与真源不一致就失败。
4. 好处是消灭了原版"系统提示词一份内核、知识库又一份内核，两边慢慢漂移"的经典退化。

## 软规则与硬规则的划分

一条规则要不要写进代码，用三个判据：

| 判据 | 含义 |
|---|---|
| 可判定 | 机器能给出明确的通过/拒绝，不靠语义判断 |
| 高频违反 | 模型在这件事上反复犯同样的错 |
| 后果不可逆 | 一旦被绕过去，记录就被污染，事后无法还原 |

三条都成立 → 进 `scripts/falsify.py`。典型例子：概率所有权、兑现后改概率、事后回填、手工改账。

只满足一两条的，留在提示词里，用"质量门 + 回归测试"约束。典型例子：是否给了反证、是否分层、是否用故事代替论证——这些没有确定性判据，硬编码只会制造假阳性。

## 失效模式与对策

| 失效模式 | 表现 | 对策 |
|---|---|---|
| 内核未触发 | 模型按自己的习惯答完，压根没用这套规则 | 触发词写进 `description`；常驻载体（AGENTS.md）兜底 |
| 工作流未读 | 声称"已按决策流程"但没读 `08-decision.md` | 输出合同要求标注读了什么；T02 测试专门抓假装加载 |
| 规则被稀释 | 长对话后段开始省略证据表 | 内核短、工作流按需、每轮自检清单 |
| 强制层不可用 | 环境没有文件读写/执行能力 | 降级为让模型只吐卡片 JSON，用户手动跑 CLI |
| 单例修补 | 一次坏回答 → 往内核塞十条新规则 | CONTRIBUTING 明确禁止；先立回归用例 |
| 评分幻觉 | 只报 Brier 不给基线/N | 报告层强制：无基线就警告，N<30 标"仅描述" |

## 与其它做法的比较

| 做法 | 优点 | 代价 |
|---|---|---|
| 一个大提示词 | 简单，随处可贴 | 注意力稀释、无法回归、改一处崩一片 |
| 知识库 + RAG | 不怕长 | 关键规则可能整轮没被召回；无法保证每轮生效 |
| 微调 | 风格稳定 | 贵、不可审计、规则改动不可见 |
| MCP 工具集 | 真正的硬约束 | 依赖具体客户端，规则与工具耦合 |
| **本项目** | 规则可读可审、载体可换、算术进代码 | 需要模型配合；行为效果必须逐载体回归 |

## 演化策略

- 规则改动必须附一条可复现的回归用例（`references/19-regression.md` 的 T 编号，或新加编号）。
- 内核膨胀有红线：`dist/kernel-always-on.md` 超过 3,000 字符时测试失败，强制先把内容挪进工作流。
- 版本语义见 [CONTRIBUTING.md](../CONTRIBUTING.md)：新增工作流 = minor；内核语义变更 = major；文案与示例 = patch。
