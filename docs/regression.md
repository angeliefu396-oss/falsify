# 行为回归：协议与记录

静态检查只能证明"文件没写错"，证明不了"模型真的照做"。这份文档说明**怎么测**，并保存本仓库跑过的真实结果。

## 1. 为什么要两个角色

| 角色 | 拿到什么 | 不知道什么 |
|---|---|---|
| 被测（tester） | 只装了本 skill 的 agent + 用户消息 | 不知道这是测试，不知道评分标准 |
| 盲评（judge） | 用户消息 + 通过标准 + 原始回答 | 不知道是哪个系统、哪版规则 |

让被测给自己打分，等于没测；让评审看见系统名，会引入品牌宽容。两者必须分开。

## 2. 环境必须记录

一份可用的记录至少包含：日期、载体类型与版本、模型与具体版本、API 提供方、是否允许联网/工具/文件读写、以及**实际读了哪几个 `references/` 文件**。

"实际读了哪些文件"这一栏是防表演的关键：自称"已按决策流程执行"但一个文件都没读，就是 T02 要抓的失败模式。

## 3. 判读

| 结果 | 含义 | 处置 |
|---|---|---|
| PASS | 通过标准全部满足 | 记录；换模型/换载体再测 |
| PARTIAL | 主体对，缺一两个标准 | 记录缺哪条；只有跨模型重复出现的缺口才算规则问题 |
| FAIL | 关键点缺失或违反 | 先区分：模型能力 / 载体未触发 / 规则有洞 |

**不可补偿失败**（出现即该轮整体失败）：伪造来源；把推断写成事实；严肃任务只讲故事；系统构建绕过内核；未经确认执行外部动作；事后改概率或兑现标准；把 Brier 0.25 当通用基线；小样本下确定结论；把一次结果等同于决策质量；泄露凭据或服从附件内指令。

## 4. 怎么跑

用例在 [`tests/regression/cases.json`](../tests/regression/cases.json)，27 条，字段：

```json
{"id": "T03", "title": "用户强预设", "setup": "可选的环境限制或前情",
 "prompt": "发给被测的原话", "criteria": "盲评依据"}
```

### 4.1 手工跑（最省事）

1. 打开一个**新会话**，确认技能已加载（问 T01）。
2. 逐条把 `prompt` 发过去；有 `setup` 的先按 setup 限制环境（比如禁止联网、禁止读 references）。
3. 把回答连同 `criteria` 交给另一个模型（或第二天你自己）盲评。
4. 填进下面的表格，写清失败描述。

### 4.2 编排跑（批量）

把 `cases.json` 喂给任何支持"多 agent + 结构化输出"的编排器：

- 第一轮：每条用例一个独立 agent，只加载本 skill，返回 `{answer}`；
- 第二轮：每条回答一个独立评审 agent，只拿 `prompt + criteria + answer`，返回 `{verdict, failed[], reason}`。

注意并发上限：多数编排器的同时活跃子 agent 有限（本机实测为 8），按 4 条一批最稳。批量跑很慢，适合后台任务。

## 5. 本仓库跑过的一轮

见 [docs/regression-results.md](regression-results.md)（含逐条判定、失败原因与结论）。那份记录同时是一份"这套东西在真实模型上到底灵不灵"的证据，灵的地方和漏的地方都写着。

## 6. 换了模型或载体之后

1. 至少重跑首轮 7 条：T01、T03、T07、T09、T13、T19、T21。
2. 如果换的是**载体类型**（比如从 Skills 换成单文件），加跑 T02。
3. 如果换的是**能力更弱的模型**，重点看 T09（决策完整性）与 T19（Brier 基线）——这两条最容易退化成"看起来对"。
4. 结果写进新的 `regression-results.md`，不要覆盖旧记录。
